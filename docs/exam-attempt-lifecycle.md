# Серверная попытка пробного тестирования

Этот документ описывает backend жизненного цикла экзамена. Следующим шагом к нему подключён новый интерфейс `/exams` — см. [описание интерфейса](exam-ui.md). Существующий QuizPage продолжает использовать прежнюю сдачу теста урока. Оценивание `calculate_kt_profile_score` не переписано. Рабочая БД не использовалась.

## Хранение и конфигурации

`ExamAttempt` хранит владельца, UUID, состояние, неизменяемые снимки конфигурации и вопросов, выбранные ID вариантов, отметки возврата, последний вопрос каждой секции, ревизию и серверный дедлайн. Пока попытка активна, Result и записи завершённой аналитики не создаются.

Миграция `quizzes/0007_exam_attempt.py` добавляет эту таблицу и поле `Quiz.exam_configuration_key`. Старые записи не превращаются в экзамены, старые результаты не переписываются. Откат с потерей новых попыток или привязок контента запрещён. Миграция проверена только на одноразовых тестовых БД, на рабочей не применялась.

Конфигурации определены в `quizzes/exam_config.py`:

- `m094_profile_ru_v1`: профильный формат, русский язык, 30 + 20 вопросов, максимум 30 + 40 баллов, 100 минут.
- `m094_scientific_ru_v1`: полный научно-педагогический формат недоступен. Нельзя запустить его на 50 профильных вопросах; материалов английского и ТГО и полного оценивания ещё нет.
- `m094_profile_ru_demo_v1`: «Демонстрация двух профильных предметов», искусственные данные, без экзаменационного таймера. Выключена по умолчанию; нужна явная тестовая настройка `EXAM_DEMO_ENABLED = True`.

Для старта нужен ровно один Quiz с соответствующим `exam_configuration_key`, режимом `kt_profile`, опубликованным курсом и корректным набором вопросов 30/20. Пустая, неоднозначная или некорректная привязка делает конфигурацию недоступной с причиной. Существующие курсы автоматически не объявляются M094. Демоданные не загружаются в рабочую БД.

## API

Все операции требуют авторизации. Доступ к попытке имеет только её владелец; чужая попытка возвращает 404, в том числе для staff. Пути ниже указаны для core service; через существующий gateway перед ними добавляется `/api`.

| Метод и путь | Назначение |
| --- | --- |
| GET `/exams/configurations/` | Конфигурации с `available` и причиной недоступности; без создания попытки |
| POST `/exams/attempts/` | Подтверждённый старт |
| GET `/exams/attempts/` | Свои попытки; фильтры `status=active\|completed`, `configuration_id`, `offset` |
| GET `/exams/attempts/{id}/` | Восстановление вопросов, ответов, отметок и позиции |
| PATCH `/exams/attempts/{id}/answers/` | Сохранение полного набора выбранных ответов |
| POST `/exams/attempts/{id}/finish/` | Завершение с актуальным полным набором ответов |
| GET `/exams/attempts/{id}/result/` | Серверные баллы завершённой попытки |
| GET `/exams/attempts/{id}/review/` | Замороженные вопросы, все выбранные варианты, ключи, объяснения и баллы |

Список возвращает `{ "results": [...], "next_offset": null }`; по 50 записей, при наличии следующей страницы `next_offset` содержит её смещение. Фильтрация выполняется до пагинации, поэтому старая активная попытка не скрывается за новыми завершёнными.

Старт:

```json
{
  "configuration_id": "m094_profile_ru_v1",
  "request_id": "00000000-0000-4000-8000-000000000001"
}
```

UUID здесь иллюстративный. Клиент создаёт новый UUID только для нового действия. Повтор старта с тем же UUID и конфигурацией возвращает ту же попытку: 201 при создании, 200 при повторе. Изменение конфигурации с прежним UUID даёт 409. Явно новый старт не удаляет предыдущую попытку; ограничение числа активных попыток не вводилось.

Сохранение и ручное завершение используют одинаковую структуру:

```json
{
  "request_id": "00000000-0000-4000-8000-000000000002",
  "revision": 0,
  "answers": [
    { "question_id": 101, "choice_ids": [1001] },
    { "question_id": 131, "choice_ids": [1301, 1303] }
  ],
  "flagged_question_ids": [131],
  "last_question_by_section": {
    "first_subject": 101,
    "second_subject": 131
  }
}
```

ID вопросов и вариантов берутся из ответа старта, а не из этого примера. `answers` заменяет полный набор ответов: отсутствующий вопрос или пустой `choice_ids` означает пропуск. Пустой `answers` очищает все ответы. Необязательные отметки при отсутствии поля сохраняются; переданный список заменяет их. Позиции обновляются только для переданных секций.

После успешного сохранения сервер увеличивает `revision`. Следующая запись использует полученную ревизию. Устаревшая запись даёт 409 и не перезаписывает новое состояние; клиент должен прочитать актуальную попытку. Повтор последнего подтверждённого сохранения с тем же UUID и содержимым возвращает 200 без новой ревизии. Реестр всех прежних UUID сохранений не ведётся: после следующего сохранения старый запрос получает конфликт версии.

Повтор ручного завершения с тем же UUID и тем же содержимым возвращает прежний результат. Иной набор ответов не заменяет завершённую попытку. Валидация проверяет типы, дубликаты, принадлежность вопросов/вариантов и одиночный выбор первого предмета; второй предмет не ограничен тремя выбранными вариантами. Баллы и правильность клиент назначить не может.

## Снимок, дедлайн и завершение

Вопросы упорядочены по секциям и ID; локальная нумерация первой секции 1–30, второй 1–20. Выбор хранится по ID, а не номеру. GET активной попытки не содержит правильных ключей, объяснений и оценок. `result`/`review` до завершения отвечают 409.

Редактирование или удаление источника не меняет снимок. Результат, детализация, все 50 ответов (включая пропуски) и переход попытки в завершённое состояние сохраняются одной транзакцией. Ошибка записи откатывает всё. Используется прежний серверный калькулятор, а не новый алгоритм. Проверяется зафиксированная версия правил: неизвестная версия отклоняется.

В новых экзаменационных результатах исходные ID и тексты берутся из снимков; необязательные связи Result/детализации/ответов с живым контентом не создаются. Это исключает появление новых FK во время удаления источника. Связь самой попытки с источником существует со старта и обнуляется при его удалении. Старые тесты уроков не меняют способ хранения. Старые отчёты по живым вопросам и подписи курса/урока не заменяют новый экзаменационный API.

Дедлайн устанавливает сервер при старте. После него новые ответы не принимаются: сервер завершает попытку по последнему подтверждённому набору. GET и корректные запросы сохранения/завершения проверяют срок под блокировкой. Время завершения просроченной попытки соответствует дедлайну. Ответ на позднюю запись — 409 `deadline_expired` с ID сохранённого результата.

Для закрытой вкладки есть команда `python manage.py finalize_exam_attempts --limit 100`: один ограниченный проход по просроченным попыткам. Периодический запуск в рабочем окружении не настроен. Без него запись результата появится при следующем обращении к попытке или ручном запуске команды; принять поздние ответы это не позволяет.

## Выполненные изолированные проверки

Из корня этой рабочей копии:

```powershell
docker run --rm --pull never --network none --read-only --tmpfs /tmp:rw,nosuid,nodev,size=256m --mount "type=bind,source=C:/Users/User/.codex/worktrees/pr-32-merge/SaqBol_LMS/services/core_service,target=/source,readonly" --entrypoint python saqbol_lms-core_service:latest /source/tests/run_training_audit.py

powershell -NoProfile -ExecutionPolicy Bypass -File services/core_service/tests/run_exam_lifecycle_concurrency.ps1
```

Первый runner использует SQLite в памяти и отключённую сеть. Второй создаёт одноразовый PostgreSQL 15 в закрытой Docker-сети, без опубликованных портов и постоянных volumes, а после удаляет только свои контейнеры и сеть. Источники копируются по разрешённому списку; рабочие настройки, секреты и пользовательские данные не используются. Нужны уже имеющиеся Docker-образы `saqbol_lms-core_service:latest` и `postgres:15`; скачивание отключено.

Проверки вызывают настоящие API/ORM. Они покрывают сохранение/восстановление, изоляцию владельцев, неизменность снимков, валидацию, прежнее оценивание, конкурирующие записи, повторную сдачу, откат при сбое и дедлайн. Это проверка backend; новый пользовательский маршрут и браузерный сценарий в этом шаге не реализованы.

Результат финального прогона 06.11.2026: **509 тестов прошли** (407 прежних и 102 новых); **11 проверок конкуренции на PostgreSQL прошли**. Применение миграций и `makemigrations quizzes --check --dry-run` успешны. До реализации прежние 407 тестов проходили, новые фиксировали отсутствие серверной функции. Отдельно воспроизведена и устранена гонка обычного удаления источника со сдачей: ошибка FK до исправления, успешные обе операции после него. Проверка `git diff --check` не выявила ошибок.
